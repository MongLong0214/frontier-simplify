# 개발 프로세스와 검증 체계

1인 메인테이너가 운영하는 초기 프로젝트다. 첫 제품은 로컬 CLI로 과제를 실행하고 결과를 파일로 저장한다고 가정한다. 목표는 실행·채점의 정확성과 평가 결과의 재현 가능성이다. 모델 성능의 변동과 도구 자체의 결함을 구분한다.

## 개발 흐름

1. 변경할 동작과 기대 결과를 짧게 적는다. 첫 구현은 고정 응답을 내는 가짜 에이전트로 `과제 로드 → 실행 → 채점 → 결과 저장`을 연결한다.
2. 작은 변경 단위로 구현하고, 틀렸을 때 사용자가 영향을 받는 동작을 테스트한다. 버그 수정에는 같은 결함을 잡는 회귀 테스트를 붙인다.
3. 첫 실행 경로가 생기면 로컬과 CI에서 같은 명령으로 포맷·린트와 오프라인 테스트를 실행한다. 메인테이너가 diff와 결과를 확인해 병합한다. 외부 기여도 같은 방식으로 검토한다.

언어와 도구를 선택한 뒤 실제 검증 명령을 README에 적는다. CI는 외부 API나 비밀키 없이 실행한다. 첫 공개 배포 때 깨끗한 환경에서 설치하고 예제 과제 실행과 결과 읽기를 확인한다. 이후 설치·패키징 변경 때 이 확인을 반복한다.

## 검증할 제품 동작

| 위험 | 검증 방법 |
| --- | --- |
| 잘못된 채점·집계 | 정답을 아는 작은 과제로 성공·실패·부분 점수와 집계 결과를 확인한다. 실패·누락 실행을 성공률 분모에서 조용히 빼지 않는다. |
| 실행 흐름의 결함 | 가짜 에이전트로 전체 경로를 테스트하고, 잘못된 입력·타임아웃·프로세스 종료·결과 저장 실패를 확인한다. 에이전트 실패와 평가 도구/API 오류를 구별해 기록한다. |
| 실행 간 간섭·채점 조작 | 실제 에이전트 코드를 실행하기 전에 격리된 임시 작업 공간, 시간·자원 제한, 종료 후 정리를 구현한다. 호스트 비밀정보와 불필요한 네트워크 접근을 차단하고, 에이전트가 수정할 수 없는 채점 기준으로 평가한다. 경계가 지켜지는지 통합 테스트한다. |
| 결과 유실·형식 오류 | 저장 후 다시 읽어 값과 오류 상태를 확인한다. 중단된 실행을 완료 결과로 취급하지 않는다. |

테스트는 구현 내부 구조보다 관찰 가능한 결과를 확인한다. 실제 모델 호출은 실행기·에이전트 연동·채점 변경의 영향을 확인할 때, 비용 한도를 정하고 수동 실행한다. 모델 점수의 단발성 하락을 일반 CI의 실패 조건으로 삼지 않는다.

## 평가 결과의 신뢰성

- 실행마다 도구 커밋, 과제·채점 기준 버전, 입력과 프롬프트, 에이전트·모델 식별자와 제공되는 버전, 설정·예산·환경·시드를 저장한다. 원본 응답, 생성 패치, 채점 로그, 실행 상태, 비용·시간도 남기되 비밀키는 기록하지 않는다.
- 비교 전에 과제 집합, 실행 예산, 반복 횟수와 재시도 규칙을 정하고 양쪽에 동일하게 적용한다. 재시도 전 실패도 보존한다. 평가 도구 오류는 성능 실패와 분리해 공개하고 비교의 제한을 밝힌다.
- 결과에는 과제별 성적, 실제 실행 횟수와 실행 간 변동을 함께 제시한다. 한 번의 실행으로 우열을 단정하지 않는다. 동일 시드도 외부 모델 응답의 재현을 보장하지 않으므로 원본 기록으로 채점을 다시 확인할 수 있게 한다.
- 공개 과제의 학습 데이터 포함 가능성과 결과의 적용 범위를 밝힌다. 과제나 채점 기준이 바뀌면 버전을 바꾸고 기존 점수와 직접 비교하지 않는다.
