# 개발 프로세스와 검증 체계

이 문서는 코드가 없는 상태에서 시작하는 AI 코딩 에이전트 평가 도구의 개발·검증·릴리스 기준이다. 메인테이너 1명이 운영한다는 전제로, 회의나 다중 승인 대신 작은 변경, 자동 검증, 기록 가능한 자기 리뷰를 사용한다.

프로세스만으로 결함이 없음을 보장할 수는 없다. 목표는 **잘못된 평가 결과를 발견하고, 근거가 부족한 결과의 공개를 막고, 문제가 생긴 결과를 추적·철회할 수 있게 하는 것**이다. 아래 명령, 파일 구조, CI 작업은 앞으로 구현할 계약이며, 현재 존재하거나 검증을 통과했다는 뜻이 아니다.

## 1. 품질의 정의와 초기 범위

품질을 기능 동작, 측정 타당성, 재현성, 안전한 실행의 네 축으로 관리한다. 테스트가 통과해도 에이전트의 실제 작업 능력과 무관한 점수를 내거나, 같은 결과를 다시 설명할 수 없다면 품질 기준을 충족하지 못한다.

첫 버전은 하나의 언어·실행 환경, 하나의 에이전트 어댑터, 하나의 결정적 채점 방식, 로컬 실행에 한정한다. 모의 에이전트와 작은 테스트 저장소로 전체 흐름을 먼저 만든다. 여러 제공자 지원, 웹 대시보드, 공개 순위표, LLM 심사, 분산 실행은 핵심 검증을 갖춘 뒤 추가한다. 첫 버전의 결과는 지원한 작업 범위에 대해서만 해석한다.

| 검증할 주장 | 필요한 증거 | 충족하지 못하면 |
| --- | --- | --- |
| 입력부터 보고서까지 올바르게 처리한다 | 오프라인 통합 테스트와 저장된 원시 기록 | 병합 보류 |
| 맞는 해결책과 틀린 해결책을 구별한다 | 알려진 정답·오답·경계 사례를 이용한 채점기 검증 | 해당 태스크 사용 중지 |
| 에이전트 때문에 난 실패를 구별한다 | 오류 분류 계약과 장애 주입 테스트 | 해당 실행을 점수 확정에 사용하지 않음 |
| 결과를 추적하고 다시 계산할 수 있다 | 실행 명세, 원시 결과, 채점기·집계기 버전 | 비교 결과 공개 보류 |
| 에이전트의 실행을 제한한다 | 격리, 자격 증명 보호, 자원 제한에 대한 검증 | 실제 에이전트 실행 보류 |

## 2. 코드를 쓰기 전에 결정할 사항

첫 작업 이슈에 다음 항목을 채운다. 구현 언어와 패키지 관리 도구는 이때 하나를 선택하고 런타임 버전과 의존성 잠금 방식을 정한다. 미정인 값이 있으면 임의의 기본값으로 실제 평가를 실행하지 않는다.

1. **측정 대상:** 예를 들어 “고정된 저장소 상태에서 버그를 수정하고, 독립된 테스트를 통과시키는 능력”. 허용된 입력·행동·산출물과 측정하지 않는 능력도 적는다.
2. **첫 실행 환경:** 지원 OS·아키텍처, 격리 방식, 언어·도구체인, 모델 접근 방식. 초기 지원 환경은 하나면 충분하다.
3. **예산:** 시행당 시간·토큰·비용·CPU·메모리·디스크·출력량 한도, 전체 배치 비용 한도와 중단 방법. 비용 상한은 확인 가능한 계량 수단이 있을 때만 보장한다고 표현한다.
4. **성공 판정:** 반드시 통과해야 할 검사, 테스트 변조 판정, 부분 점수 유무. 첫 버전은 이진 성공 판정으로 시작한다.
5. **평가 계획:** 태스크 목록, 반복 횟수, 기준 에이전트 또는 기준 버전, 비교 조건, 오류·재시도 처리, 결과 공개 범위.
6. **배포 방식:** 설치·실행 경로, 지원 인터페이스, 라이선스, 태스크 데이터와 저장소 스냅샷을 재배포할 권리.

평가 계약은 `docs/evaluation-contract.md`에 기록한다. 최초에는 아래 3~5절을 옮겨 구체화하면 된다. 설계 결정 기록은 점수 정의, 격리 경계, 데이터 형식처럼 나중에 바꾸기 어려운 선택에만 남긴다. 작은 구현 선택마다 문서를 만들지는 않는다.

## 3. 평가 계약: 결과를 보기 전에 규칙을 고정한다

### 3.1 태스크와 시행

**태스크**는 저장소 스냅샷, 문제 설명, 입력 조건, 독립된 채점 기준의 묶음이다. **시행(trial)**은 특정 태스크를 특정 에이전트 구성으로 한 번 수행하는 측정 단위다. **실행 묶음(run)**은 사전에 정한 여러 시행이다. 통신 재시도와 새 시행을 구별한다.

각 태스크에는 고유 ID와 버전, 출처·라이선스, 저장소 커밋 또는 콘텐츠 해시, 의존성 잠금 정보, 실행 이미지의 digest, 준비 절차, 시간 제한, 채점기 버전·해시를 둔다. 가능한 경우 정답 패치, 반드시 실패해야 할 무변경 상태와 대표 오답도 보관한다. 플랫폼별 차이가 있으면 지원 범위를 명시한다.

태스크를 편입하기 전에 깨끗한 환경에서 다음을 확인한다.

- 초기 상태가 의도한 이유로 실패하고, 알려진 정답은 통과한다. 이미 통과하는 초기 상태를 성공으로 세지 않는다.
- 사소하게 잘못된 패치와 문제 설명을 따르지 않은 패치를 채점기가 거부한다. 정답 패치의 모양이 아니라 요구한 행동을 검사한다.
- 설치, 시간, 임의성, 외부 서비스에 좌우되지 않는다. 불가피한 의존성은 고정하거나 별도 평가 범위로 분리한다.
- 설명만으로 풀 수 있으며 정답 파일, 채점용 비밀 정보, 다른 시행의 산출물이 입력에 섞이지 않는다.

개발 중 튜닝에 쓰는 태스크와 결과를 발표할 평가 태스크를 분리한다. 평가 태스크를 보고 프롬프트나 어댑터를 튜닝했다면 이후 결과에서 개발용 노출을 공개한다. 공개된 태스크가 모델 학습에 쓰이지 않았다고 보장하지 않는다. 암기 가능성과 실제 일반화 능력을 구분해 설명한다.

### 3.2 종료 상태와 분모

각 시행은 최종 상태 하나와 원인 코드, 에이전트 실행·채점 단계 정보를 가진다. 상태를 확정할 근거가 없으면 성공 또는 실패로 추정하지 않는다.

| 최종 상태 | 판정 예시 | 처리 |
| --- | --- | --- |
| `PASS` | 독립된 필수 검사를 모두 통과 | 유효 시행, 성공 |
| `FAIL` | 유효한 실행이지만 결과물이 기준 미달 | 유효 시행, 실패 |
| `AGENT_ERROR` | 정상 환경에서 에이전트가 잘못된 도구 호출을 하거나 실행을 완수하지 못함 | 유효 시행, 실패 |
| `BUDGET_EXCEEDED` | 사전 정의한 에이전트 시간·토큰·자원 한도 소진 | 유효 시행, 실패 |
| `INFRA_ERROR` | 실행기·어댑터 구현 결함, 의존 서비스 장애, 채점기 예외 | 미해결 시행, 점수 확정 보류 |
| `CANCELLED` | 수동 중단 또는 전체 배치 예산 소진으로 시행을 마치지 못함 | 미완료로 기록 |

에이전트가 만든 프로그램의 실패는 `FAIL`, 평가 도구 자체의 예외는 `INFRA_ERROR`다. 제공자 응답 제한·통신 장애의 처리와 과금된 실패 비용도 계약에 명시한다. 책임 소재가 불명확하면 `INFRA_ERROR`로 기록하고 조사한다. 분류를 바꿀 때는 근거와 이전 상태를 보존한다.

주 지표는 각 태스크를 같은 비중으로 세는 성공률이다. 태스크 N개를 각각 R회 평가하고 모두 해결되었다면 `PASS / (N × R)`로 계산한다. 모든 태스크에 같은 R을 적용한다. 비용·지연·오류율은 보조 지표로 함께 보고하며 성공한 시행만의 비용을 전체 비용처럼 제시하지 않는다.

미해결·미완료 시행이 있다면 완료된 것만으로 공식 점수를 확정하지 않는다. 예정 시행 수 S, 성공 수 P, 미해결·미완료 수 U와 함께 완료율을 보고하고, 필요하면 전체 성공률의 가능한 범위 `[P/S, (P+U)/S]`를 표시한다. 이는 **누락에 따른 범위이며 통계적 신뢰구간이 아니다**. 부분 실행 결과는 잠정 결과로만 공개한다.

### 3.3 비교와 재시도

- 에이전트 비교 전에 태스크·반복 수·프롬프트·도구 권한·예산·모델 설정·채점기·집계기를 고정한다. 변경되면 별도 실험으로 시작한다.
- 기본 비교는 동일한 자원 제한으로 수행한다. 제공자별 토큰 정의와 도구 기능 차이는 공개한다. 동일 비용 비교 등 다른 조건은 별도 표로 표시한다.
- 같은 태스크의 결과를 짝지어 비교한다. 외부 제공자의 시간대 영향이 있으면 실행 순서를 섞거나 교차 실행하고 순서를 기록한다.
- 반복 수는 예산에 맞춰 실행 전에 정한다. 초기 탐색은 태스크당 3회를 출발점으로 삼을 수 있지만, 충분한 표본 수를 보장하는 규칙은 아니다. 우열 주장은 태스크 다양성과 변동성을 확인한 뒤 한다.
- 반복 시행은 같은 태스크에 종속될 수 있다. 통계적 불확실성을 추정한다면 태스크를 묶음 단위로 취급하는 짝지은 방법을 사용하고 방법·가정을 공개한다. 소수 태스크에서는 개별 결과와 기술 통계를 우선한다.
- `FAIL`, `AGENT_ERROR`, `BUDGET_EXCEEDED`를 성공할 때까지 재실행하지 않는다. 전송 재시도는 횟수·대기·중복 과금 처리·예산 포함 여부를 사전에 고정한다.
- `INFRA_ERROR` 복구는 같은 `trial_id` 아래 새 `attempt_id`로 기록하고 최대 복구 횟수를 사전에 정한다. 첫 유효 attempt로 시행 결과를 확정하며 성공한 attempt를 골라 쓰지 않는다. 동일 조건 복원이 불가능하거나 수정이 측정에 영향을 주면 비교 묶음을 다시 실행한다. 모든 attempt와 원래 오류·복구 비용을 보존한다.
- 정답을 본 뒤 태스크를 빼거나 점수·프롬프트를 바꾸지 않는다. 불량 태스크는 이유를 남겨 새 태스크 집합 버전에서 제외하고 모든 비교 대상에 같은 규칙을 적용한다.

## 4. 검증 가능한 구조와 재현성

핵심 흐름은 `태스크 로딩 → 환경 준비 → 에이전트 실행 → 독립 채점 → 집계 → 보고서`로 나눈다. 어댑터는 제공자별 차이를 처리하고, 성공 판정과 점수 계산은 제공자와 독립된 코드에 둔다. 실행 중 생긴 기록을 읽는 것만으로 집계와 보고서를 다시 만들 수 있어야 한다.

시행마다 새 작업 공간을 만든다. 에이전트가 수정한 작업 공간에서 채점기를 그대로 실행하지 않는다. 채점 단계는 깨끗한 환경에 허용된 산출물만 적용하고, 신뢰된 채점 자료를 다시 주입한다. 에이전트의 “성공했다”는 출력이나 종료 코드 0만으로 성공 처리하지 않는다.

각 run의 실행 명세와 원시 기록에는 다음을 저장한다.

| 기록 | 필수 내용 |
| --- | --- |
| 식별 | run/trial/attempt ID, 예정 시행 목록, 재시도·복구 관계, 확정 attempt, 시각 |
| 평가 도구 | 커밋, 미커밋 변경 유무, 결과 스키마·채점기·집계기 버전 |
| 실행 환경 | OS·아키텍처, 런타임, 이미지 digest, 의존성 해시, 자원 제한 |
| 평가 대상 | 에이전트·어댑터 버전, 모델의 제공자 ID와 가능한 스냅샷 정보, 실제 설정·프롬프트 또는 복원 가능한 버전과 해시, 도구·네트워크 권한 |
| 태스크 | 태스크 집합·개별 태스크 버전, 저장소 해시, 반복 인덱스, 지원된다면 seed |
| 관측 | 상태와 원인, 패치·도구 호출 기록, 채점 근거, 소요 시간, 사용량, 비용 산정 근거 |

누락된 사용량·비용은 0으로 바꾸지 않고 `unknown`으로 표시한다. 요금에 따른 추정 비용과 제공자가 반환한 실제 청구 정보를 구분하고, 요금 기준일을 기록한다. 필수 명세가 없거나 지원하지 않는 스키마는 집계에서 조용히 수용하지 않는다.

재현성은 두 수준으로 구분한다. **재집계**는 보관된 원시 결과에서 같은 점수를 얻는 것이며 필수다. **재실행**은 같은 조건에서 에이전트를 다시 실행하는 것으로, 원격 모델의 변경과 비결정성 때문에 동일 출력까지 보장하지 않는다. seed를 고정해도 원격 모델이 결정적이라는 주장을 하지 않는다.

원시 기록은 덮어쓰지 않고 해시로 변경을 감지한다. 재채점·재집계는 원본 ID와 새 버전에 연결된 별도 산출물로 저장한다. 공개 결과에는 명세, 태스크별 결과, 채점·집계 버전, 알려진 제약을 포함한다. 원본 보관 위치·기간과 공개 가능한 기록 범위를 정하고, 자격 증명·개인 정보가 섞인 기록은 공개용 사본에서 제거한다. 제거 범위와 재현에 미치는 영향도 남긴다.

## 5. 실행 안전성은 실제 에이전트 연결의 선행 조건이다

에이전트 출력, 태스크 저장소, 의존성 설치 스크립트와 PR 기여 코드는 신뢰하지 않는다. 태스크 안의 지시가 평가기 설정, 자격 증명, 채점 기준을 바꿀 권한을 갖지 않게 한다.

- 실행별 격리 환경에서 비특권 사용자로 실행한다. 호스트 홈, 개인 저장소, SSH 키, 클라우드 자격 증명, 컨테이너 제어 소켓을 제공하지 않는다. 호스트 경로 쓰기는 명시한 산출물 위치로 제한한다.
- 기본 네트워크는 차단한다. 의존성은 준비 단계에서 고정·캐시하고, 모델 호출에 필요한 접근은 실행기 측 프록시 등 통제된 경로로 제공한다. 일반 작업 프로세스에 제공자 키를 직접 넘기지 않는다.
- CPU·메모리·프로세스 수·디스크·로그 크기·벽시계 시간 제한을 실행 환경에서 강제한다. 초과 시 자식 프로세스까지 종료하고 임시 작업 공간을 정리한다.
- 채점기·정답·평가 메타데이터는 에이전트 실행 중 접근할 수 없게 한다. 채점 시에도 제출 코드가 채점기, 기대값, 집계 결과를 변조할 수 없도록 읽기 권한과 쓰기 권한을 분리한다.
- CI의 외부 PR은 비밀 없는 오프라인 검사만 수행한다. 신뢰되지 않은 코드를 권한 있는 CI 컨텍스트에서 실행하거나, PR이 만든 실행 파일·캐시를 유료 평가에 그대로 사용하지 않는다.
- 제한 설정 실패, 격리 기능 부재, 정리 실패가 발생하면 실행을 거부하거나 중단한다. 경고만 출력하고 호스트에서 계속 실행하지 않는다.

격리 테스트는 임시 파일·모의 비밀 값·로컬 테스트 서비스로 수행한다. 허용되지 않은 파일 읽기·쓰기 및 네트워크 접근 차단, 시간·출력 제한, 자식 프로세스 종료, 다음 시행으로의 잔여 파일 유출 방지를 검사한다. 컨테이너 사용만으로 적대적인 코드에 대한 충분한 격리가 확보됐다고 간주하지 않는다. 처음에는 검토한 태스크를 로컬에서 실행하고, 임의의 외부 코드를 받는 서비스는 별도의 격리 설계와 검증 전까지 지원하지 않는다.

## 6. 1인 개발의 변경 흐름

작업은 가급적 며칠 이내에 검증할 수 있는 크기로 나누고 동시에 하나를 진행한다. 자신의 변경도 브랜치와 PR 또는 저장소 안의 변경 기록으로 남긴다. 승인자 수를 품질 지표로 삼지 않는다. 자동 검증 결과와 메인테이너의 근거 있는 자기 리뷰가 병합 조건이다.

| 단계 | 수행 내용 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 준비 | 문제, 사용자에게 달라질 행동, 비목표, 인수 조건, 위험 등급을 적음 | 성공·실패를 판정할 예가 있음 |
| 검증 설계 | 계약과 독립된 기대값, 실패 사례, 필요한 검사를 정함 | 무엇이 결함을 잡는지 설명 가능 |
| 구현 | 하나의 인수 조건을 끝까지 연결하고 필요한 회귀 검사를 추가 | 로컬 필수 검사 통과 |
| 자기 리뷰 | 최종 diff, 오류 경로, 기록·예산·호환성 영향을 확인 | 아래 완료 기준을 충족 |
| 병합 | 검증한 최종 커밋을 병합 | 필수 CI 성공; 이후 변경 시 관련 검사 재실행 |
| 배포 | 버전·변경 이력·산출물을 확정하고 릴리스 검증 | 9절 릴리스 조건 충족 |

단순 오탈자는 별도 설계 이슈 없이 변경 설명으로 충분하다. 공개 기여에도 같은 기준을 적용한다. 로직을 구현한 AI가 제안한 기대값을 그대로 정답으로 삼지 않는다. 메인테이너가 작은 수작업 예제나 명세에서 기대값을 확인하며, AI 리뷰는 자동 검사와 이 확인을 대체하지 않는다.

### 위험에 따른 검증 강도

| 등급 | 예시 | 필수 검증 |
| --- | --- | --- |
| 낮음 | 설명 문구, 출력 꾸밈, 동작을 바꾸지 않는 문서 | diff·참조·예시 확인, 적용되는 기존 빠른 검사. 구현을 복제하는 테스트는 추가하지 않음 |
| 보통 | CLI 옵션, 입력 파서, 어댑터 매핑, 일반 오류 처리 | 관련 단위·계약 테스트, 오프라인 통합 검사 |
| 높음 | 성공 판정, 분모, 재시도, 격리, 비용 제한, 결과 스키마, 태스크 집합 | 회귀 fixture, 경계·실패 검사, 기존 결과 재집계, 전후 차이 설명, 복구 방법 |

높은 위험의 변경은 별도 PR로 분리한다. 한 번은 구현 관점으로, 한 번은 실제 사용자와 결과 소비자 관점으로 최종 diff와 증거를 검토한다. 두 관점의 리뷰를 했다는 이유만으로 독립된 제3자 검증이라고 표현하지 않는다. 미해결된 의문이 있으면 새 기능을 끄거나 변경을 줄인다.

### 병합 완료 기준

- [ ] 인수 조건을 충족하고 필요한 실패·경계 사례를 확인했다.
- [ ] 위험에 맞는 검사를 최종 커밋에서 통과했다. 미실행 항목은 이유와 영향이 적혀 있다.
- [ ] 점수·예산·오류 분류·격리·스키마에 영향이 있는지 명시했다.
- [ ] 실패를 성공으로 보이게 하는 기본값, 예외 무시, 무제한 재시도가 없다.
- [ ] 사용자 동작이나 공개 인터페이스가 바뀌면 문서와 변경 이력을 수정했다.
- [ ] 결과가 달라지면 원인을 설명하고, 필요 시 프로토콜 버전과 이전 결과의 상태를 갱신했다.
- [ ] 비밀 정보, 재배포 권한이 불분명한 데이터, 불필요한 의존성이 포함되지 않았다.

체크리스트에는 적용되지 않는 항목을 `N/A`와 이유로 표시한다. 필수 검사가 실패했거나 실행되지 않았다면 검증 완료로 표시하지 않는다.

## 7. 검증 계층과 회귀 방지

테스트 수와 커버리지 비율 자체를 출시 목표로 삼지 않는다. 아래 중요 실패가 실제로 검출되는지 우선 확인한다. 커버리지는 점수 계산·상태 전이·예산·격리 경로에서 빠진 분기와 오류 처리를 찾는 보조 수단으로 사용한다.

| 계층 | 검사 대상과 대표 사례 | 실행 시점 |
| --- | --- | --- |
| 정적 검사 | 형식, lint, 언어에 맞는 타입 검사, 비밀 정보 검사 | 모든 코드 PR |
| 단위·속성 검사 | 분모·반올림, 빈 평가 계획 거부, 상태 전이, 누락 필드, 중복 ID, 음수 사용량, 경계 예산 | 모든 코드 PR |
| 어댑터 계약 | 정상 응답, 잘못된 응답, 통신 장애, 사용량 누락, 취소, 제한된 재시도 | 어댑터 변경과 릴리스 |
| 오프라인 통합 | 작은 저장소 + 모의 에이전트 → 패치 → 독립 채점 → 원시 기록 → 보고서 | 모든 코드 PR |
| 채점기 검증 | 정답 통과, 무변경·대표 오답 실패, 검사 변조로 통과하지 않음 | 채점기·태스크 변경과 릴리스 |
| 실행기 검증 | 접근·자원 제한, 강제 종료, 정리, 중단·재개 시 중복 집계 방지 | 실행기·환경 변경과 릴리스 |
| 패키지 검증 | 깨끗한 환경에 배포 산출물 설치 후 문서의 첫 실행 수행 | 릴리스 후보 |
| 실제 제공자 스모크 | 인증, API 호환성, 도구 왕복, 사용량 기록 | 관련 변경 후와 릴리스 전, 정한 예산 내 |
| 품질 회귀 평가 | 고정 태스크·조건의 이전 기준 결과와 비교 | 측정 경로 변경 또는 성능 주장 시 |

첫 회귀 fixture에는 다음을 포함한다.

1. 통과·실패·에이전트 오류·예산 초과·인프라 오류·취소 각각의 기록과 기대 보고서.
2. 예정 4회 중 성공 2회, 실패 1회, 인프라 오류 1회인 경우: 완료 3/4, 누락 범위 50~75%, 공식 점수 미확정. 완료된 3회만의 66.7%를 확정 점수로 내지 않는다.
3. 같은 attempt 기록을 두 번 읽어도 중복 집계하지 않는 경우. 같은 attempt ID의 서로 다른 기록은 오류로 처리하고, 복구 attempt가 여러 개여도 시행 하나로 집계한다.
4. 입력 순서가 달라도 집계가 같고, 저장·복원·재집계 후 점수가 같은 경우.
5. 시간 초과, 채점기 예외, 알 수 없는 사용량이 성공·0원으로 변환되지 않는 경우.
6. 에이전트가 자체 테스트를 바꾸거나 성공 메시지만 출력해도 독립된 검사에서 걸러지는 경우.

고정 기대값은 작은 사례에서 직접 계산한다. snapshot/golden 파일을 바꿀 때는 차이가 생긴 이유를 리뷰에 적으며, 실패한 테스트를 통과시키기 위한 일괄 갱신을 하지 않는다. 높은 위험의 채점·집계 변경에서는 대표 조건 하나를 의도적으로 잘못 바꿨을 때 관련 테스트가 실패하는지도 확인한다. 처음부터 전체 mutation testing 체계를 운영할 필요는 없다.

LLM 채점이 나중에 필요해지면 고정된 인간 판정 표본과의 일치도, 순서·표현 변화에 대한 안정성, 프롬프트 주입 내성을 별도로 검증한다. 심사 모델·프롬프트·불확실 판정·재검토 규칙을 버전 관리하고 결정적 테스트 결과와 구분한다. 이 조건을 갖추기 전에는 공식 성공 판정에 사용하지 않는다.

## 8. CI와 비용 운영

실제 명령은 도구체인 선택 후 아래 세 진입점으로 묶는다. 로컬과 CI에서 같은 명령을 사용한다. 예시는 `make`를 사용한 이름이며 특정 도구 채택을 요구하지 않는다.

| 진입점 | 계약 | 실행 환경 |
| --- | --- | --- |
| `make check` | 정적 검사, 단위·계약 검사, 작은 오프라인 통합. API 키와 유료 호출 없이 실행 | 모든 PR의 필수 검사 |
| `make verify-release` | 전체 오프라인 회귀·채점·격리·설치 검사. 필요한 격리 기능이 없으면 실패 | 지원 환경의 릴리스 후보 |
| `make eval-smoke` | 명시한 태스크·제공자로 소규모 실호출. 배치·시행 한도와 결과 기록 필수 | 메인테이너가 검토한 커밋에서 수동 실행 |

빠른 PR 검사는 최초 목표를 5분 이내로 두되, 실제 실행 시간을 측정해 조정한다. 이를 맞추려고 중요한 검사를 삭제하지 않고 무거운 환경 검사를 분리한다. 초기에는 최소 지원 환경만 CI로 검증하며, 지원한다고 선언한 플랫폼은 해당 검증을 추가한 뒤 공개한다.

유료 평가는 모든 PR에서 실행하지 않는다. 모의 응답으로 재현할 수 없는 제공자 호환성 변화와 릴리스 확인에 사용한다. 순수 문서 변경에는 생략 가능하다. 실제 제공자가 검증되지 않았다면 해당 지원 상태를 명시하고 검증 완료로 표시하지 않는다. 고정 태스크를 대상으로 한 스모크 통과를 일반적인 성능 향상 증거로 사용하지 않는다.

의존성은 잠그고 CI 외부 작업의 참조도 불변 식별자로 고정한다. 의존성 업데이트는 한 묶음씩 검증하며, 관련 보안 공지는 주간 점검에 포함한다. 비용 한도는 실행 전에 확인하고 새 시행 시작 전 남은 예산을 검사한다. 동시 실행 비용은 예약분까지 계산한다. 계량 지연 때문에 비용 상한을 엄밀히 보장할 수 없다면 별도 제공자 제한, 토큰 한도와 보수적인 여유를 사용하고 그 한계를 문서화한다.

불안정한 테스트는 자동 재시도로 녹색 상태를 만들지 않는다. 원 실패와 재시도 결과를 보존하고 원인 이슈를 만든다. 비핵심 검사의 임시 제외는 이유·담당자·만료일·대체 검증을 기록한다. 점수 정확성, 필수 명세, 격리·자격 증명, 예산 중단 검사는 제외 대상이 아니다. 관련 필수 검사가 불안정하면 해당 경로의 병합 또는 릴리스를 멈춘다.

## 9. 릴리스와 평가 결과 공개

도구 릴리스와 벤치마크 결과 공개는 별도 결정이다. 패키지가 동작해도 비교 데이터가 불완전하면 순위나 우열 주장을 공개하지 않는다.

도구 버전, 평가 프로토콜 버전, 태스크 집합 버전, 결과 스키마 버전을 분리해 기록한다. 점수 정의·태스크·예산·채점기가 바뀌면 새로운 비교 조건이다. 같은 차트에 이전 결과를 이어 붙이지 않는다. 도구가 초기 버전이어도 CLI·파일 형식의 파괴적 변경은 변경 이력에 명시하고 이전 파일을 명시적으로 거부하거나 변환 방법을 제공한다.

릴리스 후보에서는 다음을 확인한다.

- [ ] 태그를 붙일 커밋과 실제 배포 산출물이 일치하며, `check`와 `verify-release`가 통과했다.
- [ ] 깨끗한 지원 환경에서 설치, 모의 에이전트 실행, 결과 재집계를 README만으로 수행했다.
- [ ] 제공자 지원에 필요한 스모크 결과가 있고, 알려진 제약과 지원 환경이 문서에 반영되어 있다.
- [ ] 평가 결과 왜곡, 격리 실패, 비밀 노출, 예산 제한 실패에 해당하는 미해결 결함이 없다.
- [ ] 라이선스, 기여 방법, 보안 제보 방법, 변경 이력, 결과 형식과 복구 방법을 제공한다.

결과 공개에는 추가로 고정된 평가 계획, 모든 예정 시행의 처리 내역, 기준 결과, 개별 태스크 결과, 불확실성·노출 이력·비용 산정 근거가 필요하다. 태스크별로 좋은 결과만 뽑아 비교하지 않는다. 메인테이너가 자신의 도구나 에이전트를 평가한다면 이해관계와 튜닝 범위를 밝힌다.

첫 공개는 실험적 상태로 표시하고 품질·성능 보장의 범위를 좁힌다. 날짜에 맞추기 위해 위의 차단 결함을 예외 승인하지 않는다. 일정을 줄여야 한다면 기능이나 지원 범위를 줄인다.

## 10. 결함, 결과 정정과 운영

| 우선순위 | 기준 | 대응 |
| --- | --- | --- |
| P0 | 비밀 노출, 격리 경계 실패, 무제한 실행·비용 발생 | 관련 실행·배포 중단, 자격 증명 폐기 등 피해 제한, 영향 범위 조사 |
| P1 | 잘못된 점수·분모·채점, 결과 혼합·유실, 필수 메타데이터 오류 | 관련 결과를 잠정 무효로 표시하고 공개·릴리스 중단 |
| P2 | 우회 가능한 일반 기능·문서·사용성 문제 | 재현 조건과 우회 방법을 기록하고 계획에 반영 |

결함을 발견하면 영향을 받는 도구·프로토콜·태스크·결과 버전을 먼저 식별한다. 가능한 최소 fixture로 재현하고 회귀 검사를 추가한 뒤 고친다. 점수·채점 변경은 기존 기록을 재집계할 수 있는지 확인하고, 관측 자체가 잘못됐다면 다시 실행한다. 공개된 결과는 삭제로 감추지 않고 영향, 철회·대체 상태, 수정 결과 링크를 남긴다. 비밀이 포함된 원본은 별도로 접근을 제한하거나 제거한다.

되돌리기는 이전 검증된 도구·프로토콜·환경 조합으로 복귀하는 것이다. 코드만 되돌려 서로 다른 태스크나 스키마의 결과를 섞지 않는다. 장시간 실행의 중단·재개는 시행 ID와 완료 기록을 기준으로 하며, 불완전한 파일을 완료된 결과로 읽지 않는지 검증한다.

1인 운영에서는 즉시 응답 SLA를 약속하지 않는다. 주 1회 짧게 실패한 CI, 불안정한 태스크, 보안·의존성 변경, 비용, 제보를 확인한다. 결과 왜곡 결함 수, 원인을 분류하지 못한 시행 수, CI 실패 원인과 소요 시간, 실제 지출을 추적한다. 지표에 변화가 없다면 새 보고 체계를 추가하지 않는다. 릴리스 후에는 놓친 결함을 막을 수 있었던 검사 하나를 선정해 보강한다.

## 11. 구현 착수 순서와 단계별 종료 조건

| 단계 | 구현·산출물 | 종료 조건 |
| --- | --- | --- |
| 0. 계약 고정 | 첫 지원 환경·예산 선택, 평가 계약, 태스크·결과 스키마 초안 | 정답·오답·오류·미완료 예제의 기대 결과를 손으로 판정할 수 있음 |
| 1. 세로 기능 구현 | 모의 에이전트, 작은 태스크 1개, 채점·저장·집계·CLI, `check` | 네트워크·API 키 없이 실행부터 보고서까지 재현하고 오류 기록도 확인 |
| 2. 실행 경계 검증 | 격리·자원 제한·정리·안전한 채점, `verify-release` | 5절의 제한 검사가 지원 환경에서 통과; 실패 시 실행이 중단됨 |
| 3. 실제 연결 | 어댑터 1개, 기록·계량·예산 중단, `eval-smoke` | 제한된 실제 실행에서 도구 호출과 비용 근거를 확인하고 모든 시행 상태를 설명 가능 |
| 4. 평가 신뢰성 | 검토한 작은 태스크 집합, 기준 결과, 정답·오답 검증, 비교 보고서 | 모든 예정 시행을 추적하고 원시 기록에서 점수가 재생성됨 |
| 5. 첫 릴리스 | 설치 산출물, README, LICENSE, CONTRIBUTING, SECURITY, 변경 이력 | 9절 도구 릴리스 조건 통과; 결과 발표 시 추가 공개 조건도 통과 |

초기 태스크 집합은 5~10개 정도로 운영 부담을 확인할 수 있지만 대표성을 입증하는 규모로 간주하지 않는다. 태스크 수보다 각 태스크의 올바른 판정과 장애 설명 능력을 먼저 확보한다. 다음 언어·제공자·채점 방식을 추가할 때마다 같은 계약과 검증 계층을 확장한다.

문서는 `process.md`, 평가 계약, 사용자 안내를 중심으로 시작한다. 기여·보안 안내는 외부 기여를 받기 전에 작성한다. 팀 회의, 별도 승인 위원회, 24시간 운영, 매일의 대규모 유료 벤치마크는 초기 운영 요건으로 두지 않는다. 자동 검증과 결과 추적에 필요한 장치부터 구현한다.
