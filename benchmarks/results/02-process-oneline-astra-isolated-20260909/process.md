# 개발 프로세스와 검증 체계

코드가 없는 1인 오픈소스 프로젝트를 위한 시작 기준이다. 모든 결함을 없애는 절차보다, 잘못된 채점·비교·실행을 빠르게 발견하는 검증에 집중한다. 이 문서는 프로세스 설계이며, 아래 명령과 검사는 구현하면서 만든다.

## 1. 첫 구현의 범위

첫 목표는 **작은 과제 하나를 입력받아 → 에이전트를 실행하고 → 독립적으로 채점하고 → 결과를 저장하는 전체 흐름**이다. 에이전트 연동 하나와 로컬 실행부터 시작한다. 여러 제공자 지원, 분산 실행, 리더보드는 실제 필요가 생길 때 추가한다.

과제에는 입력, 허용된 작업 범위, 성공 조건, 실행 예산을 둔다. 실행기는 에이전트 연동과 채점기를 분리해, 가짜 에이전트와 고정된 산출물로 전체 흐름을 검증할 수 있게 한다.

## 2. 평소의 개발 흐름

변경 하나마다 다음 순서로 작업한다. 별도 설계서나 승인자를 요구하지 않는다.

1. **기대 동작을 정한다.** 무엇이 달라지고 어떤 관찰로 성공을 확인할지 짧게 적는다. 기존 이슈나 PR이 있으면 그곳에, 없으면 커밋 설명에 남긴다. 이를 위해 이슈나 PR을 새로 만들 필요는 없다.
2. **중요한 동작을 검증한다.** 버그 수정은 수정 전 실패하는 회귀 테스트를 먼저 만든다. 기능 추가는 정상 경로와 영향이 큰 실패 경로를 검증한다. 문구·서식 수정처럼 동작이 바뀌지 않으면 관련 부분 확인으로 충분하다.
3. **작게 구현하고 검사한다.** 한 변경에는 한 목적을 담고, 아래의 공통 검사를 실행한다.
4. **차이를 직접 검토하고 반영한다.** 테스트가 요구 동작을 확인하는지, 채점·격리·결과 호환성에 영향을 주는지 살펴본다. 검증 방법과 알려진 제한은 같은 커밋 또는 PR 설명에 간단히 남긴다.

혼자 작업할 때는 직접 커밋해도 된다. 외부 기여는 PR에서 메인테이너가 검토하며, 동일한 자동 검사를 적용한다. 문서 승인, 별도 QA 승인, 필수 인원수는 두지 않는다.

## 3. 평가가 지켜야 할 규칙

### 채점과 실패 분류

- 성공 여부는 에이전트의 자기 보고가 아니라 사전에 정한 검증기로 판정한다. 초기에는 실행 가능한 테스트 등 객관적인 기준을 사용한다.
- 제출물이 바꾼 테스트를 그대로 신뢰하지 않는다. 채점 기준과 원본 검증 자료는 에이전트의 수정 권한 밖에 보관하고, 채점에는 신뢰된 사본을 사용한다.
- 결과 상태는 최소한 `pass`, `fail`, `error`로 구분한다. `pass`는 기준 충족, `fail`은 유효한 평가에서 기준 미충족, `error`는 도구·인프라 문제로 판정 불가다.
- 사전에 정한 에이전트 시간·호출·비용 한도 초과는 `fail`과 구체적인 사유로 기록한다. 제공자 장애나 실행기 고장은 `error`다. 원인이 불명확한 실패를 임의로 에이전트 성적에 넣지 않는다.
- 보고서는 성공·실패·오류 수와 전체 과제 수를 함께 표시한다. 성공률은 `pass / (pass + fail)`로 분모를 명시하고, 유효한 평가가 없으면 계산하지 않는다. 오류 때문에 실행 범위가 다른 결과를 그대로 순위 비교하지 않는다.
- 재시도는 기본적으로 하지 않는다. 필요하면 조건과 횟수를 실행 전에 정하고 모든 시도를 남긴다. 가장 좋은 시도만 골라 성적으로 쓰지 않는다.

### 실행 격리

- 에이전트와 생성된 코드는 과제별 격리 환경에서 실행한다. 임시 디렉터리만으로 격리를 대신하지 않는다.
- 호스트 파일, 자격 증명, 다른 실행의 산출물에 접근하지 못하게 한다. 모델 API 키는 호출을 중계하는 실행 제어부에만 두고 과제 실행 환경에 전달하지 않는다.
- 네트워크는 기본 차단하고 과제 수행에 필요한 대상만 허용한다. 시간, 자원, 출력 크기와 호출 예산을 제한하고 종료·취소 뒤 자식 프로세스와 작업 공간을 정리한다.
- 이 경계가 준비되기 전에는 개발자가 작성한 고정된 모의 산출물로 검증한다. 실제 에이전트가 생성한 코드를 호스트에서 바로 실행하지 않는다.

### 추적 가능성과 비교

실행 결과에는 다음 정보와 다시 채점할 수 있는 산출물을 함께 저장한다. 기록은 결과 형식의 일부로 두며, 별도 수기 보고서를 만들지 않는다.

| 정보 | 최소 기록 |
| --- | --- |
| 평가 정의 | 도구 커밋, 과제·채점기 버전 또는 해시, 과제 출처 |
| 실행 조건 | 에이전트 버전, 제공자·모델 식별자, 설정, 프롬프트, 적용 가능한 시드, 실행 시각 |
| 환경·예산 | 런타임·의존성 또는 이미지 식별자, 시간·자원·호출 한도 |
| 관측 결과 | 상태와 사유, 제출 변경분, 검증 출력, 소요 시간, 가능한 경우 토큰·비용, 시도 이력 |

비밀값은 저장하지 않으며 공개 로그는 민감정보를 제거한다. 수집할 수 없는 값은 추정값과 구별해 미수집으로 표시한다.

같은 산출물을 고정된 검증기에 넣으면 같은 판정이 나와야 한다. 반면 실제 모델의 응답은 시드를 고정해도 재현이 보장되지 않는다. 비교할 때는 과제, 채점기, 환경, 예산을 맞추고 반복 횟수와 결과의 변동을 공개한다. 한 번만 실행했다면 단일 실행 관측으로 표시한다. 과제·채점 기준을 바꾸면 버전을 바꾸고 이전 점수와 직접 섞지 않는다. 공개 과제의 학습 데이터 포함 여부를 모르면 그 한계도 밝힌다.

## 4. 최소 자동 검증

스택을 선택하면 로컬과 CI에서 같은 명령 하나로 검사하도록 만든다. 아래에서는 이를 `check`라고 부르며, 실제 명령은 선택한 스택에 맞춘다. 명령은 서식·정적 검사와 필요한 테스트를 실행한다. 타입 검사는 사용하는 언어와 설정에 맞게 포함한다.

자동 검사는 외부 모델 API 없이 실행한다. 고정된 응답을 내는 가짜 에이전트와 작고 결정적인 과제로 다음을 확인한다.

| 대상 | 반드시 확인할 동작 |
| --- | --- |
| 채점 | 정답 산출물은 통과하고 오답·빈 산출물·검증 자료를 임의 변경한 산출물은 통과하지 않는다. |
| 실행과 오류 | 정상 완료, 에이전트 예산 초과, 제공자 오류, 채점기 고장을 구분하고 결과를 빠짐없이 저장한다. |
| 격리와 정리 | 허용 범위 밖의 쓰기·금지된 네트워크 접근이 차단되고, 시간 초과·취소 후 실행 자원이 정리된다. 격리 경계를 바꾸면 이 검증을 갱신한다. |
| 전체 흐름 | 작은 과제를 입력해 실행·채점·결과 저장까지 완료하고, 저장된 산출물을 다시 채점하면 같은 판정을 얻는다. |
| 보고서 | 통과·실패·오류가 섞인 결과의 집계가 맞고, 유효 결과가 없는 경우도 처리한다. |

테스트는 내부 함수 호출 순서보다 외부에서 관찰되는 동작을 확인한다. 커버리지 수치를 반영 조건으로 삼지 않는다. 새로운 위험이나 실제 결함이 드러날 때 해당 회귀 테스트를 추가한다.

CI는 처음에 주 지원 환경 하나의 작업으로 시작한다. 공통 검사가 통과하는 것을 유일한 일상 반영 조건으로 두고, 실패하면 수정하거나 변경을 되돌린다. CI가 반영 뒤 실행되는 직접 커밋도 같은 원칙으로 처리한다. 간헐적으로 실패하는 검사는 재실행 성공만으로 넘기지 않고 원인을 수정하거나, 검증하지 못하는 범위를 명시하고 해당 기능의 지원을 제한한다.

외부 기여 코드의 CI에는 비밀값을 제공하지 않는다. 실제 모델 호출은 기본 CI에서 제외하며, 연동 변경 시 명시적인 예산을 설정한 작은 수동 실행으로 연결·응답 처리·결과 기록을 확인한다. 실제 응답의 정답률을 단위 테스트의 합격 조건으로 쓰지 않는다.

## 5. 공개할 때만 추가로 확인할 것

- **버전 배포:** 배포할 커밋의 공통 검사 통과를 확인하고, 깨끗한 환경에서 배포물 설치 후 작은 과제 하나의 전체 흐름을 실행한다. 사용자 동작이나 결과 형식이 달라졌다면 릴리스 설명에 적는다.
- **성능 결과 공개:** 위 실행 기록으로 비교 조건을 확인할 수 있게 하고, 실행 수·오류·변동·제한을 함께 공개한다. 채점 동작이 바뀌었다면 비교 대상도 같은 채점기로 다시 평가한다. 비용 때문에 재평가하지 못하면 비교 주장을 제한한다.
- **공개 후 결함:** 재현 사례를 회귀 테스트로 남기고 수정한다. 채점 결함이면 영향을 받은 결과를 무효로 표시하고 수정된 버전으로 다시 평가한다.

처음부터 별도 품질 위원회, 다단계 브랜치, 의무 설계 문서, 매 변경 전체 벤치마크 실행을 만들지 않는다. 절차를 늘릴 때는 실제로 반복된 문제를 해결하는 가장 작은 자동 검사나 규칙 하나부터 추가한다.
